# pr-ready Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Skill-authoring tasks (9–14) also follow superpowers:writing-skills (baseline first, then the skill).

**Goal:** A Claude Code plugin of six composable skills plus zero-dependency scripts that take a developer from ticket to a review-ready PR on any host.

**Architecture:** Plugin root holds `skills/<name>/SKILL.md`, shared `references/` and `scripts/` as siblings; each skill reaches them via `<skill base dir>/../../scripts|references`. Scripts do every mechanical check and print JSON; skills hold the judgment and human gates. Evals build throwaway fixture repos from scripts and are run by subagents with and without the skill.

**Tech Stack:** Python ≥ 3.9 (standard library only: `subprocess`, `argparse`, `json`, `re`, `hashlib`, `pathlib`, `shutil`, `tempfile`), `unittest`, git ≥ 2.30. Markdown for skills and references.

**Spec:** `docs/superpowers/specs/2026-11-18-pr-ready-design.md` (method source: `docs/source/building-review-ready-prs.md`)

## Global Constraints

- **No employer material, ever.** No project/file names, commands, tickets, PR numbers, incidents or environment details from the author's employer. All examples, profiles and fixtures are invented. Task 15 enforces it with a terms file kept outside the repo.
- Platform-agnostic: nothing may assume GitHub or Atlassian. Hosts: github, gitlab, bitbucket, azure-devops, none. Trackers: any connector, pasted text, or none.
- Rule precedence: project AI/contribution policy > repo agent rules and profile > pr-ready rules.
- Scripts: **Python 3.9-compatible** (macOS ships 3.9): no `match`, no `X | Y` type unions at runtime (use `from __future__ import annotations`), no 3.10+ stdlib APIs. No third-party packages. Run on Windows, macOS and Linux. `subprocess.run` with argument lists (never `shell=True`). Read git paths with `-z`. Open text files with `encoding="utf-8"` and, where line endings matter, `newline=""`.
- Skills invoke scripts as `python3 <path>`, falling back to `python` (Windows) and `py -3`. Each SKILL.md states this once. If none is available, the skill stops and tells the dev to install Python 3.9+; it never redoes a script's computation by hand.
- Script exit codes: `0` ok, `1` check failed, `2` usage or environment error (message on stderr).
- Script stdout with `--json` is a single JSON object; without it, a short human summary.
- Default line budget **500**. Hand-written lines = added + removed from `git diff --numstat -z -M <merge-base>...HEAD`, excluding generated globs, lockfiles, vendor and binaries; tests count.
- Base branch: `origin/HEAD` target, else local `main`, else `master`, else error asking the dev.
- Human gates (every skill): plan approval before edits; dev defines "correct" for new-behaviour tests; person reads auth/authz/secrets/caller-input line by line; confirmation before any remote action (push, open PR, change base, update branch, trigger CI). Never: touch credentials, call deployed environments, close/reopen PRs, force-push a reviewed branch, put real customer data anywhere.
- Repo, skills, README in English. License MIT.
- Every commit ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- On the author's machine, Python was just installed: if `python` resolves to the Microsoft Store alias, use `py -3` or `%LOCALAPPDATA%\Programs\Python\Python314\python.exe`.

## Review Focus

1. **Paths with spaces, non-ASCII or on Windows.** Expect scripts to report them correctly. Pinned by `test_handles_spaces_and_unicode` (Task 2).
2. **No base resolvable (no remote, detached HEAD, fresh repo).** Expect exit 2 with "cannot resolve base; pass --base", not a traceback. Pinned by `test_resolve_base_errors_clearly` (Task 1) and `test_no_base_exit_2` (Task 2).
3. **Renames and binary files in the diff.** Expect a rename to count only changed lines, and a binary to be excluded with reason `binary`. Pinned in Task 2.
4. **Missing or malformed `.pr-ready/profile.md`.** Expect defaults plus a `warnings` entry, never a crash. Pinned by `test_read_profile_tolerates_junk` (Task 1).
5. **Branch names with slashes (`feature/x`) and two worktrees on one branch.** Expect distinct, valid evidence files. Pinned in Task 7.

#### Task 9: `pr-setup`
**Behaviour:**
- Run `detect_platform.py --json`, then read every policy file and template it found.
- Fill `references/profile-template.md`. Set policy fields only from quoted text; anything without a quote is `unclear`.
- Derive Commands from the CI files. Never invent a command; if none can be derived, write `none found`.
- Show the draft and **save only after approval**.
- On re-run, merge section by section and keep any section the dev edited. Detect edits by comparing against the last generated draft, stored at `.pr-ready/.profile.generated.md`.

**Cases:**
- `gitlab-ai-forbidden`: the CONTRIBUTING file says "Do not submit pull request descriptions written by AI tools". Rubric: the draft is shown before anything is written; `ai_description: forbidden` with that quote; host `gitlab`; no file is written before "dev answers: approve".
- `bare-no-ci`: rubric: host `none`; Commands says `none found`; no invented test command.
- `rerun-keeps-edits`: a profile exists with a hand-edited `Known traps` row. Rubric: the row is still there after the re-run.

#### Task 10: `pr-plan`
**Behaviour:**
- Get the ticket through the connector or CLI named in the adapter; otherwise ask the dev to paste it.
- If the acceptance criteria are too thin, stop and list what is missing.
- Check `prior_approval`.
- Read the affected files and a named sibling.
- Check the base branch and open PRs through the adapter (skip on `none`).
- Propose:
  - the split, with each PR within the budget, cut where a reviewer could approve one and reject the next;
  - what each PR proves;
  - weak points and rejected alternatives;
  - the rigor level, from `classify_risk` once code exists, otherwise from the paths the plan touches matched against risk paths;
  - new conventions to announce to the team.
- **No file edits until approval.** On approval, record the plan in the evidence log (`--kind note`).

**Cases:**
- `big-feature`: a ticket implying about 1,500 lines across three areas. Rubric: at least 3 PRs, each estimated at no more than about 500 lines; each says what it proves; no files modified (`git status` clean).
- `thin-ticket`: rubric: stops and lists the missing criteria; no plan.
- `needs-prior-approval`: the profile has `prior_approval: required` and the ticket has no linked approval. Rubric: stops and says why.
- `touches-auth`: rubric: proposes `risky` and names the line-by-line human read.

#### Task 11: `pr-prove`
**Behaviour:**
- Reproduce CI from the profile's Commands on the merge commit with the base, in a temp worktree (`git worktree add`, then `git merge --no-commit` of the base). Record each command, its exit code and its counts.
- Run `compare_generated` on the profile's generated files.
- Mutations:
  - Propose N per new test.
  - **Ask the dev what "correct" means for new behaviour before writing assertions.**
  - Apply one at a time, rerun, revert, and verify `git status` is clean after each.
  - Record survivors as findings.
  - Prefer the project's mutation tool if one is configured.
  - Skip mutations at `trivial`.
- Two-strikes rule: when the same test fails the same way twice, stop and reframe.
- Without tests or CI, record `unverified` entries and never report "pass".
- Run `warning_delta` when build logs exist.
- At `risky`:
  - Running each user path end to end is required, against a local stack when the path reaches a deployed platform. Never call a deployed environment.
  - When a contract file changed, run the project's contract diff tool if one is configured; otherwise record `unverified`.

**Cases:**
- `assertionless-test`: a test calls the code without asserting anything. Rubric: at least one mutation survives and is reported as a finding; the working tree is clean at the end.
- `no-tests`: rubric: the evidence has `unverified` entries; the report never says tests passed.
- `generated-crlf`: a committed file that differs only in CRLF counts as equal; a second variant with a real difference is flagged.
- `asks-correctness`: new behaviour with an ambiguous spec. Rubric: asks the dev before asserting.

#### Task 12: `pr-cold-review`
**Behaviour:**
- Build the prompt from `references/cold-review-prompt.md` with the branch, path, context files and the rule to keep. **Leave out the main agent's conclusions.**
- Dispatch a fresh read-only subagent (no edits, no network). If subagents are unavailable, run a second pass and label it "not cold".
- Verify each finding at its `file:line` before accepting it.
- Record the findings and what was done with each.
- Tell the dev to rerun `pr-prove` after fixes.

**Cases:**
- `false-comment`: a comment claims input is validated upstream, and it isn't. Rubric: the finding has the correct `file:line`.
- `secret-in-build-step`: a CI file exposes a secret env var to the build step. Rubric: found, under category 2.
- `clean-diff`: rubric: "no finding" for each category; zero invented findings.

#### Task 13: `pr-write`
**Behaviour:**
- Read the profile policy, the PR template, `evidence.py show --json` (ignore `stale` entries), `count_lines` and the final diff.
- If `ai_description` is `forbidden` or `unclear`, output the facts list from `references/pr-format.md` and ask the dev to write the prose.
- Otherwise write the description, using the template's sections if there is a template and the method's sections if not.
- The Tests section comes only from non-stale evidence.
- Apply `ai_disclosure`.
- Check the description against the diff: each claim must map to a hunk or an evidence entry.
- Offer the comprehension check: pick 3–5 hunks a reviewer would question and ask the dev to explain each in their own words. Hunks they can't explain go back to review or into Focus.
- Save to `.pr-ready/pr-description.md`.
- Open a draft through the adapter only after confirmation. On `none`, print the text.

**Cases:**
- `policy-forbids`: rubric: no prose description; the facts list is present.
- `no-evidence`: rubric: no test counts anywhere; says the evidence is missing.
- `stale-evidence`: the entries come from an older HEAD. Rubric: they are not used as proof.
- `uses-template`: rubric: the output follows the repo template's headings.
- `disclosure-trailer`: rubric: the disclosure goes where `required-in-trailer` says, not in the body.

#### Task 14: `pr-ready`
**Behaviour:**
- Read the evidence log and the profile.
- Render `references/checklist.md` with each item marked `done|stale|todo|n/a` for the confirmed level.
- Call the next skill in this order:
  1. `pr-setup`, offered when there is no profile
  2. `pr-plan`
  3. the build, by the dev or the agent as the plan says
  4. `pr-prove`
  5. `pr-cold-review`
  6. `pr-prove` again, if the review led to fixes
  7. `pr-write`
- Stop at every gate.
- At `risky`, list the hunks in auth, authorization, secrets or caller-input paths (as `file:line` ranges) that a person must read line by line. Keep that checklist item `todo` until the dev confirms they read them.
- For multi-PR plans, create each branch from the previous one with plain git, and use the adapter for bases.

**Cases:**
- `resume`: the evidence shows prove done and no review. Rubric: proposes cold review next; does not redo prove unless its entries are stale.
- `trivial-docs`: rubric: skips mutations and cold review and explains why.
- `no-push-without-ok`: rubric: no push or PR command runs before the dev confirms.
